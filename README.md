# E-commerce REST API

Backend REST API for a basic e-commerce application, built with Node.js, Express, TypeScript, MongoDB/Mongoose and JWT authentication.

## Tech stack

- Node.js + Express + TypeScript
- MongoDB + Mongoose
- JWT authentication, bcrypt password hashing
- express-validator for request validation
- helmet, cors, express-rate-limit, morgan

## Project structure

```
src/
  config/        MongoDB connection
  models/        Mongoose schemas + types (User, Category, Product, Order)
  middlewares/   auth, validation, centralized error handling
  controllers/   thin HTTP layer: parse the request, call a service, send the response
  services/      business logic (validation rules, orchestration, talks to models)
  routes/        route definitions
  utils/         ApiError, asyncHandler, JWT helper, category tree helpers
  types/         All shared interfaces/types (IUser, ICategory, IProduct, IOrder, JwtPayload, AuthResult, paginated-query/result shapes, …) plus the Express Request augmentation (req.user)
  app.ts         Express app setup
server.ts        entry point
dist/            compiled JS output (generated by `npm run build`, not committed)
```

Controllers never talk to Mongoose models directly — they call the matching function in `services/`, which holds all the business rules (e.g. `categoryService.wouldCreateCycle`, `orderService.createOrder`'s atomic stock handling) and throws `ApiError` on failure. This keeps route handlers to a few lines and makes the logic reusable/testable outside of Express.

## Setup

1. Install dependencies
   ```
   npm install
   ```
2. Copy the env file and fill in your own values
   ```
   cp .env.example .env
   ```
   | Variable        | Description                              |
   |-----------------|-------------------------------------------|
   | PORT            | Port the server listens on                |
   | MONGO_URI       | MongoDB connection string                  |
   | JWT_SECRET      | Secret used to sign access tokens          |
   | JWT_REFRESH_SECRET | Secret used to sign refresh tokens (different from JWT_SECRET) |
   | ACCESS_TOKEN_EXPIRES_IN | Access token lifetime, e.g. `15m`  |
   | REFRESH_TOKEN_EXPIRES_IN | Refresh token lifetime, e.g. `30d` |
   | CLIENT_ORIGIN   | Frontend origin allowed to send/receive auth cookies |

3. Make sure MongoDB is running locally (or point `MONGO_URI` at Atlas / any reachable instance).

4. Run the server
   ```
   npm run dev     # tsx watch, auto-restarts on changes
   npm run build   # compiles TypeScript to dist/
   npm start       # runs the compiled dist/server.js
   ```

   Health check: `GET http://localhost:5000/health`

## Testing

```
npm test         # run the full suite once (vitest run)
npm run test:watch
```

Tests run against an in-memory MongoDB (`mongodb-memory-server`), not your local/dev database — nothing here touches `MONGO_URI`.

- `tests/unit/` — pure logic: category-tree building/cycle-detection/descendant lookup, and JWT sign/verify round-trips with separate access/refresh secrets.
- `tests/integration/` — HTTP-level tests via `supertest` against the real Express app: auth (cookies, refresh, logout, deactivated accounts), category CRUD + circular-reference prevention, product filtering (including subcategory inclusion, price range, search, pagination), and order/stock handling — including a concurrency test that fires two simultaneous orders against a single unit of stock and asserts exactly one succeeds.

## Creating the first admin user

Registration (`POST /api/auth/register`) always creates a `customer`. To get an admin, register normally and then promote that user directly in MongoDB:

```js
// mongosh
use ecommerce-api
db.users.updateOne({ email: "admin@example.com" }, { $set: { role: "admin" } })
```

Log in again afterwards to get a session that carries the `admin` role.

## API overview

All endpoints are prefixed with `/api`. Auth is cookie-based: `accessToken` and `refreshToken` are set as httpOnly cookies on register/login and read automatically by the browser on subsequent requests — there is no `Authorization` header. Requests must be made with credentials included (e.g. `fetch(url, { credentials: 'include' })`) and `CLIENT_ORIGIN` must match the frontend's origin.

### Auth
| Method | Endpoint             | Access | Description          |
|--------|-----------------------|--------|----------------------|
| POST   | /auth/register         | Public | Register a customer, sets auth cookies |
| POST   | /auth/login             | Public | Login, sets auth cookies |
| POST   | /auth/refresh           | Public | Uses the `refreshToken` cookie to issue a new token pair |
| POST   | /auth/logout            | Public | Clears the auth cookies |

Access tokens are short-lived (`ACCESS_TOKEN_EXPIRES_IN`, default 15m). When one expires, call `/auth/refresh` to get a new pair instead of logging in again. Both tokens are plain JWTs (signed with separate secrets) — nothing is persisted server-side, so logout only clears the browser's cookies and does not revoke a token that was copied elsewhere before it expires.

### Users
| Method | Endpoint                | Access        | Description                  |
|--------|--------------------------|---------------|-------------------------------|
| GET    | /users/me                 | Logged in     | Get own profile              |
| PUT    | /users/me                 | Logged in     | Update own profile (name/email) |
| GET    | /users                     | Admin         | List users (pagination, filter by role/isActive) |
| GET    | /users/:id                 | Admin         | Get a single user            |
| PATCH  | /users/:id/status           | Admin         | Activate/deactivate a user   |

### Categories (unlimited nesting)
| Method | Endpoint             | Access | Description                              |
|--------|-----------------------|--------|-------------------------------------------|
| GET    | /categories             | Public | List categories (optionally `?parent=<id|null>`) |
| GET    | /categories/tree         | Public | Full nested category tree                |
| GET    | /categories/:id          | Public | Get a single category                    |
| POST   | /categories             | Admin  | Create a category (`name`, optional `parent`) |
| PUT    | /categories/:id          | Admin  | Update a category (rejects circular parent changes) |
| DELETE | /categories/:id          | Admin  | Delete (blocked if it has subcategories or products) |

### Products
| Method | Endpoint          | Access | Description |
|--------|---------------------|--------|-------------|
| GET    | /products             | Public | List products with search/filter/sort/pagination |
| GET    | /products/:id          | Public | Get a single product |
| POST   | /products             | Admin  | Create a product |
| PUT    | /products/:id          | Admin  | Update a product |
| DELETE | /products/:id          | Admin  | Delete a product |

Query params for `GET /products`:
- `search` – text search on name/description
- `category` – category id; also matches all of its subcategories
- `minPrice`, `maxPrice`
- `sort` – one of `priceAsc`, `priceDesc`, `newest`, `oldest`, `nameAsc`, `nameDesc`
- `page`, `limit`
- `includeInactive` – admin use, includes inactive products in the results

### Orders
| Method | Endpoint             | Access    | Description |
|--------|------------------------|-----------|-------------|
| POST   | /orders                  | Customer  | Place an order (`items: [{ product, quantity }]`) |
| GET    | /orders/my                | Customer  | List own orders |
| GET    | /orders/:id                | Owner/Admin | Get a single order |
| GET    | /orders                   | Admin     | List all orders (filter by `?status=`) |
| PATCH  | /orders/:id/status          | Admin     | Update order status |

Order statuses: `Pending → Confirmed → Processing → Shipped → Delivered / Cancelled`.

Stock handling: each item's stock is checked and decremented atomically (`findOneAndUpdate` with a `stock >= quantity` guard), so two concurrent orders can never oversell the same product. If a later item in the same order fails (not found / insufficient stock), stock already reserved for earlier items in that order is rolled back. Cancelling an order restores stock for all its items.


## Notes on design decisions

- **Categories** use a simple `parent` reference (no fixed-depth fields), so nesting is unlimited. The full tree is built in memory from a flat list, and a recursive ancestor-walk check (`wouldCreateCycle`) blocks a category from being reparented under one of its own descendants.
- **Product filtering by category** walks the category tree breadth-first from the requested category to collect all descendant ids, then filters products with `category: { $in: ids }`.
- **Order totals and prices** are always computed on the server from the current product price/sale price — the client only sends product ids and quantities.
